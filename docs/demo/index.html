What is a software factory?

A factory, for software

A software factory is a written pipeline that every piece of work follows. Agents do each stage the same way every time, scripts check the result, and people approve at the gates. It turns “ask an assistant to write some code” into a process you can repeat, inspect and trust.

The parts of a factory

Six words to know

Six words describe the whole thing.

PipelineThe stops a piece of work passes through, in order.
StageOne job. Done by an agent, or by a script.
SkillHow a job is done, written down once.
GateWhere the work waits for a person to approve.
EvidenceProof a section passed, written by a checker.
Background jobPicks up new work and keeps it moving.
How it is organised

One factory, many repositories

There is one factory: one editor and one background job. It serves as many repositories as you like, and each repository has one or more pipelines, such as one for features, a shorter one for bugs, and one that reviews pull requests. This demo runs five pipelines across two repositories. One limit to know: a single pipeline works on one repository, so an idea that spans two is two issues today.

The factoryOne editor and one background job, on one machine.
RepositoriesAs many as you like. This demo uses two: an API and a UI.
PipelinesEach repository has one or more: features, bugs, reviewing pull requests.
Chapter 1 · Set up

Set up the factory, once

Three steps, done once per machine.

1Get the factory

Clone it. It needs Python, Claude Code, and a login to your tracker.

Do this yourself
git clone https://github.com/sanjeev23oct/software-factory.git
cd software-factory

2Open the editor

Everything from here is done on a page, not in files.

Do this yourself
python3 factory/editor.py

3Start the background job

It checks for new work every ten minutes. Nobody has to start anything again.

Do this yourself
python3 factory/scripts/schedule.py install --every 10
python3 factory/scripts/schedule.py status
Chapter 2 · Define a pipeline

Give a repository its pipeline

Seven steps in the editor. These frames show a real pipeline being created: feature work on the UI repository.

4Add a repository

Tell the factory where the code is and give the pipeline a name.

5Pick a starting point

Start from an example and edit it, or from nothing. Examples are not fixed types.

6Say what triggers it

Which repository, which label, and who the issue must be assigned to.

7Arrange the stages and gates

The stages are the work. The gates are where a person approves.

8Give the pipeline its skills

A skill is a short document that says how one kind of job is done. Maker skills are the ones a task can name. For each, you say which files it is for; when tasks are written, every task gets the skill that fits the file it touches, and a script rejects a task that names the wrong one. Bring skills in from the library, import the ones your team already keeps in the repository, or write your own.

Do this yourselfOpen the Skills tab. Add a skill, fill in Files it is for, and save.

9Write the rules

The team's rules in plain words, and the commands that prove a change works.

10Switch it on

From here the background job watches this repository.

Chapter 3 · Run

From idea to value

One idea, written as an issue, taken all the way to a pull request in about ten minutes of work. A person decided twice; everything else was done by agents in separate sessions and checked by scripts.

11Write the idea down

An issue in the tracker, in plain words, with the label and the assignee.

12The factory picks it up

Nobody starts it. The background job finds the issue on its next pass.

13Approve the requirements

The pipeline stops at its first gate. A person reads, then decides.

14A maker builds, a checker proves

Every task names the skill that builds it. The factory starts a maker session, which builds one section and may not tick anything or write evidence. It then starts a checker in a different session, which never saw the maker work: it runs the section's gate against what was built, writes the evidence, and ticks the tasks only if everything passed. The factory rejects a maker that ticks its own work and a checker that edits code, and it stamps each evidence file with both session ids. In this run four sections were each built in one session and proved in another, eight sessions in all, using the logic, view, page and tests skills.

How the build stage works

Maker, checker, script

MakerBuilds one section, with the skill each task names. May not tick a task or write evidence.
CheckerA different session that never saw the maker work. Runs the gate, writes the evidence, ticks the tasks.
ScriptRe-runs the checks itself. Rejects a maker that ticks, or a checker that edits code.

15Look at the result, and approve

The second gate is for a person to look at what was built.

16Ready to merge

The pipeline ends with a pull request. Merging it is a person's decision, and that is where the idea becomes value.

Chapter 4 · More pipelines

Other pipelines, same factory

The same factory runs other pipelines at the same time. On the API repository, feature work has two gates before any code, because API changes are costly to undo. Bugs take a short pipeline with no spec: reproduce with a failing test, fix, review, then one gate. A bug filed in this demo went from issue to a reviewed fix in under three minutes.

Chapter 5 · Review

No process, no review

A review pipeline checks pull requests, whoever wrote them. A script goes first: is there a spec, does every task name a skill, is there evidence, did the tests change with the code, plus the team's own rules. A quick hack added by hand was stopped by the script and cost nothing. The request the factory built passed all 11 checks, and only then did an agent review the code.

Do this yourselfLabel a pull request factory-review. Set the rules in the editor's Review rules tab.
What this demo produced

Seven ideas in, seven pull requests out

Across two repositories and five pipelines, seven issues became seven open pull requests, each with a spec or a reproduction, a checker's evidence, and passing tests. A person approved thirteen gates and will decide what to merge.
