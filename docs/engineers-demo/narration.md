# Inside a software factory: narration

One line per scene, timed to `engineers-demo.mp4` (7:03). "Starts" is when the scene appears; each line fits its scene at about 150 words a minute.

| # | Starts | Length | On screen | Narration |
|---|---|---|---|---|
| 1 | 0:00 | 16s | Inside a software factory | You already use Claude Code. This is what happens when you stop driving every session yourself, and build a factory that does it: how it's organised, what it checks, and how it gets better. |
| 2 | 0:16 | 24s | Three steps | AI coding has moved in three steps. First, an assistant on your laptop: you prompt, you check every edit. Then remote agents: you type a prompt in the Claude app on your phone, and it builds in a cloud sandbox. And in parallel, factories: not about where the agent runs, but how the work is organised. |
| 3 | 0:40 | 20s | A factory changes who decides, who checks, and what's recorded | Side by side. Local and remote agents differ mostly in where they run. A factory changes who decides, who checks, and what's recorded: requirements you approve before anything is built, a separate checker agent, evidence for every check, and two approvals instead of one. |
| 4 | 1:00 | 20s | Agents write all the code | Here's the definition I find most useful, from Dru Knox at Tessl. A software factory is any agentic system where all of the code you ship is written by agents. Your job changes: you stop building the product, and build the machine that builds it. |
| 5 | 1:20 | 18s | Autonomy first | How do you measure a factory? Three numbers, in order. Autonomy: how often a person has to correct or nudge the agents. Automation: how much runs without anyone reviewing it. And quality. You earn automation by proving autonomy first. |
| 6 | 1:38 | 18s | Verification makes it safe | What makes autonomy safe is verification. You can only stop reading every line if something else checks it, every time, and leaves a record you can inspect. Without that, a factory is just a faster way to ship mistakes. |
| 7 | 1:56 | 23s | Three loops | And a factory runs in three loops. The inner loop: agents iterate before anything goes up for review, fast and cheap. The outer loop: the thorough checks that replace review time. And the meta loop: it reads the corrections and failures, and fixes the factory itself, so the same mistake doesn't happen twice. |
| 8 | 2:19 | 20s | Eleven stages: agents write, scripts check, a person approves twice | Here's the factory I built, on Claude Code. Eleven stages. Scripts read the issue, lint the plan, re-check the evidence, run the tests, publish a preview, and open the merge request. Agents write the requirements, the plan, and the code. And a person approves twice. |
| 9 | 2:39 | 18s | The pipeline is data: who does each stage, and how | The pipeline is just data. Each stage says who does it, an agent, a script or a human, which skill it follows, and what it may write. A stage can fail three times before the factory stops and asks a person. |
| 10 | 2:57 | 20s | A skill: how one kind of job is done | And each kind of job has a skill: a short written instruction the agent follows. This one is for UI logic. Pure functions, no DOM, no clock. And notice the last line: the maker doesn't tick its own task or write its own evidence. |
| 11 | 3:17 | 5s | One request, start to finish | Let's watch one real request go through it. |
| 12 | 3:22 | 10s | An issue in plain words, labelled for the factory | It starts as an issue in GitLab, in plain words, with the factory label. A webhook starts a pass straight away. |
| 13 | 3:32 | 10s | The first gate: approve the requirements | Within a minute the requirements agent has written the request up, and the factory stops at the first gate. |
| 14 | 3:42 | 10s | Stories with acceptance criteria every later stage is held to | Requirements are user stories with acceptance criteria. Everything downstream is checked against these, so this approval actually means something. |
| 15 | 3:52 | 9s | Approve: one word on the issue | The reply is one word on the issue. No slash: GitLab swallows a comment that's only slash-approve. |
| 16 | 4:01 | 12s | The plan: sections, skills, and a gate for each | Then the plan. The work is split into sections, each naming the skill to use, and each ending in a gate the checker must pass. |
| 17 | 4:13 | 14s | Runnable checks, written before the code | And these are the checker's gates, written in the plan before any code exists. Runnable commands with expected results: the module's exports, no DOM or network access, currency formatting, and totals exact to the cent. |
| 18 | 4:27 | 18s | Inner loop: maker builds, a separate checker verifies | This is the inner loop. A maker session builds a section. A separate checker session, which never saw the maker work, runs the gate. Pass, and the next section starts. Fail, and a fresh maker gets the written findings. |
| 19 | 4:45 | 10s | Evidence: what was run, expected, and found | The checker writes its evidence: each check, expected, found, and a verdict. Four sections in this run, four passes, first time. |
| 20 | 4:55 | 12s | Outer loop: evidence re-checked, tests, preview | Then the outer loop: a script re-runs the evidence checks rather than trusting them, the full test suite runs, and a preview goes up. |
| 21 | 5:07 | 8s | Try it: the real change, running | The person who asked tries the real thing in a browser, and approves again. |
| 22 | 5:15 | 9s | A merge request with the specs and evidence | And a merge request opens, with the specs and every evidence file linked. Merging stays with a human. |
| 23 | 5:24 | 24s | Webhook, runner, flow.py, claude -p, state in git | How it runs. A GitLab issue or comment fires a webhook. That starts a pipeline on a runner. Each pass restores the factory's state from a branch, runs flow dot py through the stages, launches claude dash p for each agent stage, pushes the work branch, comments on the issue, and saves its state again. |
| 24 | 5:48 | 25s | The loops, made concrete | Mapped to the loops. Inner loop: maker and checker per section, three attempts. Outer loop: scripts and tests, then a person tries it. And the meta loop: every time a person has to step in, it's recorded on the issue, and the fix goes into a skill or the rules. Honestly, today that loop is me, by hand. |
| 25 | 6:13 | 15s | 17 minutes, 10 agent sessions, about $1.24, 4 of 4 first time | The numbers from that run. Seventeen minutes from issue to merge request, approvals included. Ten agent runs. About a dollar twenty at API prices. And every section passed its checker first time. |
| 26 | 6:28 | 19s | What it doesn't do yet | And the limits. Checks prove the checks pass, not that the spec was right, which is why a person approves it. The meta loop is still manual. The runner works one request at a time. And it's best on small, clear requests. |
